# DSH 插件项目设计规范（完整版）

> **版本**：v1.0
> **生效日期**：2026-09-05
> **性质**：低频修订原则 + 高频操作细则
> **适用对象**：所有参与 dsh-session-tag-manage 插件研发的设计类任务（Agent 与人员）
> **编制依据**：改编自《Web 前端设计规范 v2.4》，结合 DeepSeek Harness (DSH) 插件体系、Cordis 插件框架、OpenSpec 工作流特性定制；技术栈与领域约定以 `openspec/config.yaml`、`AGENT.md` 为准


## 第一部分：核心原则与红线

### 第一章 总则

#### 1.1 序言
本部分规定 DSH 插件研发活动中必须遵循的根本原则与不可触碰的红线。所有操作性细节（模板、量化方法、分级规则等）委托给第二部分《操作细则》动态维护，但**不得与本部分任何条款冲突**。

#### 1.2 适用范围
本部分适用于 DSH 插件架构设计、跨层契约设计（宿主 HTTP 路由 / 投影注册 / 客户端槽位）、插件新功能开发、会话事件模型扩展、投影 schema 变更、配置 Schema 设计、性能优化等所有设计类任务。

涉及**跨层契约（宿主接口、投影注册、客户端槽位）、会话数据结构（SessionEvent 变体）、投影 schema（SessionProjectionMap / SessionProjectionStateMap）** 的变更，任何情况下不可豁免本部分约束。


### 第二章 核心原则（四支柱）

| 支柱 | 内容 | DSH 插件语境示例 |
|------|------|------------------|
| **原则一：多方案比选** | 每个设计任务必须输出 **≥3 个方案**（上限不超过 5 个），方案间须有实质性技术差异，禁止伪方案。确因场景限制无法提供 3 个时，须书面说明理由并经用户同意。 | 数据通路三选一：客户端本地汇总（投影 + 槽位）vs 宿主权威计时 + RPC 拉取 vs 宿主主动推送；写通路二选一：Typert RPC vs ctx.webServer HTTP 路由；渲染挂载：CSS 类名定位 vs 槽位注入 |
| **原则二：多维度评估** | 每个方案必须从**扩展性、稳定性、可维护性、上下游依赖影响、收益评估、成本评估**六个维度进行完整评估，缺失任一维度即视为方案不完整。 | 新增投影 key 时须评估：对 SessionEventMap 声明合并的影响、客户端 useProjection 读取成本、dsh 版本兼容性、卸载清理成本等 |
| **原则三：确认后执行** | 方案未经用户明确确认，禁止开始执行。确认后须复述方案要点，确保理解一致。模糊回复（如"再看看""继续"）不视为确认。 | 遵循 OpenSpec 工作流：explore → propose → apply-change；提案必须经用户确认后才能进入执行阶段 |
| **原则四：禁止静默变更** | 执行中遇方案缺陷、环境不符、新需求、未覆盖边界等情况，必须立即停止，走变更确认流程，禁止擅自修改后继续执行。 | 如投影 API 因 dsh 版本升级（rc.x → rc.1）签名变化，必须停止并按 L3 流程重新评估，禁止直接改代码绕过 |

> **跨层契约前置核对**：涉及宿主接口、投影注册、客户端槽位、会话事件模型的改动，必须先查阅 `docs/` 下官方 API 核对文档（`dsh-session-manager.md` / `dsh-tidychat.md`），并对照 `git-source/` 内 harness 源码实证，禁止凭记忆假设契约。


### 第三章 禁止事项（红线清单）

| 编号 | 禁止行为 |
|------|----------|
| **P1** | 未提供 3 个实质性方案即要求确认或开始执行 |
| **P2** | 输出仅有名称或参数不同的伪方案 |
| **P3** | 未分析优缺点、收益及成本即输出方案 |
| **P4** | 将用户模糊回复视为确认并开始执行 |
| **P5** | 执行中修改方案后**静默继续**，未走变更流程 |
| **P6** | 变更方案未经完整评估即重新执行（分级标准见第二部分） |
| **P7** | 用户提出矛盾需求时，不停止澄清、擅自选择一侧推进 |
| **P8** | 修改宿主框架（`node_modules`、`@deepseek-ai/*`）里的任何内容 |
| **P9** | 涉及跨层契约（宿主接口、投影注册、客户端槽位）的改动，未先查阅 `docs/` 官方 API 核对文档即实施 |
| **P10** | 涉及会话数据结构、投影 schema 的改动，未先告知用户 |
| **P11** | 客户端绕过类型化 Typert RPC 或宿主注册的 `/dsh-session-host-*` HTTP 接口，直接访问宿主数据源 |
| **P12** | 客户端触碰自身锚点定位 DOM 节点区域之外的宿主 DOM |
| **P13** | 敏感凭证（API Key、数据库连接串等）硬编码进代码或配置 |

> P8 ~ P13 为项目专属红线，源自 `AGENT.md` 安全与合规要求，优先级与 P1 ~ P7 相同。


### 第四章 豁免与例外

- **可豁免多方案流程**（但须遵守其他原则）：单行修复类微调（改文案、改 CSS 值、改明显笔误）；用户已书面指定唯一实现方式的任务（如强制要求使用 Typert RPC）。
- **不可豁免**：任何涉及**跨层契约（宿主接口、投影注册、客户端槽位）、会话数据结构、投影 schema、配置 Schema 结构性变更**的改动，即便用户要求简化，也必须走完整流程。


### 第五章 第一部分与第二部分的关系

- 第二部分《操作细则》是本部分的实施细则，可随项目演进迭代更新。
- 第二部分中的任何条款不得与本部分冲突。若冲突，以本部分为准。
- 本部分的修订须记录版本历史及修订理由，且须经过与制定时同等层级的评审。


## 第二部分：操作细则

### 第六章 方案输出细则

#### 6.1 数量与质量
- 最少 3 个方案，**最多 5 个方案**（防止选择瘫痪）。
- **"实质性差异"在 DSH 插件语境下指在以下层面存在本质不同**：
  - **数据通路**：事件驱动 vs 投影驱动 vs 独立存储（如标签写 SessionEvent vs 存独立 KV vs 纯客户端状态）
  - **权威侧**：宿主权威计算 + 客户端拉取 vs 客户端本地汇总
  - **跨层通信**：Typert RPC（构建时类型化）vs ctx.webServer HTTP 路由（轻量手写校验）
  - **渲染挂载**：投影 + 客户端槽位注入 vs CSS 类名定位（MutationObserver 兜底）
  - **判定策略**：规则前置 + LLM 兜底 vs 全量 LLM 判定 vs 全量规则判定
- 仅修改变量命名、颜色值或注释内容视为无效方案。
- 若确因场景限制无法提供 3 个方案，须在方案开头明确说明限制原因，并经用户书面同意。

#### 6.2 评估维度详解（统一口径，DSH 插件示例）

| 维度 | 评估要点 | 评级与量化标准参考（DSH 插件语境） |
|------|----------|------------------------------------|
| **扩展性** | 新会话事件、新投影 key、新插件接入成本；SessionEventMap 声明合并是否顺畅；是否遵循"一切皆插件"与投影哲学 | **高**：新事件/投影仅通过 `declare module` 声明合并或 `ctx.sessionProjections.register` 接入，无需修改既有模块；**中**：需少量适配（新增配置项、扩展事件变体、加 inject 依赖）；**低**：需重构事件监听编排或投影注册结构 |
| **稳定性** | ctx.effect 生命周期托管、插件卸载/会话销毁自动回收、投影 apply 纯同步无副作用、错误边界与降级、dsh 版本兼容性 | **高**：定时器/订阅全部 `ctx.effect` 托管，卸载自动回收；投影 `apply` 纯同步、无关事件返回同一引用（`Object.is` 相等 → 零下游工作）；有降级与回滚预案；**中**：有常规 try-catch 但无降级；**低**：关键流程无容错、事件处理含副作用、dsh 版本兼容性未知 |
| **可维护性** | 模块按功能点拆分（单文件 ≤800 行）、TypeScript 强类型（禁止 any）、注释四层结构、测试覆盖率、圈复杂度 | **高**：逻辑清晰，模块职责单一（如 config / events / tagger / rules / projection / override 分文件），单元测试易写；**低**：大量副作用、深层嵌套、难以调试 |
| **上下游依赖影响** | **上游（方案依赖方）**：`@deepseek-ai/*` 依赖（cordis、dsh-session/types、dsh-session-projection 等）、Schemastery Schema、dsh 版本兼容性（rc 阶段存在破坏性变更预告）。**下游（方案影响方）**：SessionEventMap 声明合并的扩散影响、投影 schema 变更对客户端读取方的影响、公共类型/工具函数（events.ts、rules.ts）被引用后的连锁反应 | **低影响**：无新增上游依赖；影响仅限当前插件模块内部，无跨包引用扩散<br>**中影响**：需升级 1～2 个 `@deepseek-ai/*` 补丁版本，或修改少量公共类型定义，影响限于宿主或客户端单侧<br>**高影响**：依赖核心基础库大版本升级（如 dsh rc.1 投影 API 破坏性变更）；修改底层共享类型或跨层契约（SessionEventMap / 投影类型表 / 槽位），需协调宿主 + 客户端双侧回归验证 |
| **收益评估** | 从 4 个子维度综合评定：**扩展收益**（对未来事件/功能追加的适应能力）、**稳定收益**（错误捕获、降级恢复质量）、**可维护收益**（可读性、调试效率、测试覆盖）、**异常场景覆盖收益**（边界情况：会话销毁、插件卸载、投影缺失、dsh 版本差异） | 收益尽量量化（如"规则前置后 LLM 调用量下降 60%"、"异常终止识别延迟从 7 分钟降至即时"、"新增同类插件耗时预计减少 50%"）；难以量化时提供可观测改善迹象 |
| **成本评估** | 从 4 个子维度综合评定：**影响范围**（波及的插件数、模块数、跨层契约数、下游依赖数量）、**异常场景代价**（会话数据异常、插件加载失败时的恢复/回滚复杂度）、**开发成本**（开发 + 自测 + 联调 + 兼容性验证人天）、**维护成本**（文档维护、dsh 版本升级适配、技术债务偿还） | 成本统一以**人天**为单位（1 人天 = 8 小时有效工作），须明确子项拆分（如"开发 3 人天 + 自测 1 人天 + 契约联调 1 人天"） |

#### 6.4 输出模板（分级使用）

- **标准方案（≥3 个）**：包含优缺点、六维评估详细评级表、对比总表、推荐意见。
- **轻量方案（仅限豁免场景）**：仅需输出核心思路（200 字内）+ 理由说明 + 风险提示，无需完整六维评级。


### 第七章 确认与执行流程

#### 7.1 明确确认规则
- **视为"明确确认"的关键词列表**（白名单）：
  - "选择方案 X / 选第 N 个"
  - "同意 / 确认 / 可以 / 开始执行"
  - "按方案 X 执行"
- **视为"未确认"的模糊回复**：
  - "再看看""继续""稍等""行吧"（无明确指向）
  - 仅提出疑问但不附带确认意向（如"这个方案为什么用投影而不是事件流？"）
  - 超过 **48 小时**无回复（超时条款）
- **超时处理**：用户 48 小时未确认，Agent 须发送一次催办提醒；若再经过 24 小时（累计 72 小时）仍无明确回复，则该设计任务**自动挂起**，Agent 停止推进并归档当前方案，待用户重新激活。

#### 7.2 确认后动作
Agent 须复述所选方案的核心技术路线、关键假设和主要风险（如"采用事件写入 + 投影纯同步 fold + CSS 类名定位渲染，兼容 dsh 0.1.0-rc.x ~ rc.1，风险在于投影 API 在 rc.1 有破坏性变更需按目标版本核对"），用户回复"确认无误"后方可进入执行阶段。若用户发现复述有偏差，须回到方案调整阶段。

#### 7.3 变更流程（三级分级处理，DSH 插件场景示例）

| 变更等级 | 适用情形（DSH 插件示例） | 处理要求 |
|----------|--------------------------|----------|
| **L3（重大变更）** | 变更会话数据结构（新增/修改 SessionEvent 变体如 `session-tag/*` 事件契约）；修改投影 schema 与类型表（stateSchema / wire / SessionProjectionMap / SessionProjectionStateMap）；修改跨层契约（宿主 HTTP 路由路径或请求/响应契约、客户端槽位、Typert RPC contract）；配置 Schema 结构性变更 | 按第六章 6.4 完整模板重新输出修正方案，等待用户确认 |
| **L2（一般变更）** | 新增投影 key（复用既有 schema 模式）；新增 HTTP 路由（遵循既有 `/dsh-session-host-*` 模式）；调整事件判定规则（规则前置集、LLM 兜底提示词、分析延迟）；新增 `@deepseek-ai/*` 依赖；调整插件配置默认值 | 输出**简化变更说明**（变更原因 + 原/新差异对比 + 影响范围），等待用户确认 |
| **L1（轻微调整）** | 修改 CSS 样式值（标签背景色/边框）；调整文案；添加调试日志；更新依赖补丁版本 | **执行后**在进度汇报中主动说明偏差及原因，无需提前等待确认，但必须记录 |

> ⚠️ 任何变更均**禁止静默执行**（L1 可执行后报备，但不得隐瞒）。

#### 7.4 矛盾需求处理
若用户在不同节点提出相互矛盾的要求（如"必须零 Token 成本"与"所有场景必须 LLM 语义判定"），Agent 必须：
1. **立即停止**当前推进；
2. 列出矛盾点清单，以表格形式呈现冲突内容；
3. 请用户明确优先级排序，或给出取舍原则；
4. 用户澄清后，按新的优先级重新评估或选择方案。


### 第八章 评估量化指引（DSH 插件专属指标）

- **成本量化**：必须使用统一单位 **"人天"** （1 人天 = 1 人有效工作 8 小时）。按以下子项拆分明细：
  - 开发人天（代码编写）
  - 自测人天（单元测试、功能自测，如 tagger 规则判定测试）
  - 联调人天（宿主/客户端契约联调、Typert RPC 桩生成验证、投影推帧验证）
  - 兼容性验证人天（目标 dsh 版本 rc 差异核对、浏览器端行为验证）
  - 文档更新人天

- **收益量化**：优先使用以下 DSH 插件可观测指标（若适用）：
  - **扩展性收益**：新增同类插件/新事件的预估耗时变化（如"从平均 4 小时降至 1.5 小时"）
  - **稳定性收益**：预期事件判定准确率提升比例、插件崩溃率下降比例、异常终止识别时效提升（如"从延迟 7 分钟降至即时"）
  - **可维护性收益**：代码圈复杂度预计降低幅度、单元测试覆盖率提升幅度
  - **异常场景覆盖收益**：边界场景覆盖数量增加（会话销毁、插件卸载、投影缺失、dsh 版本差异）、LLM Token 消耗下降比例（规则前置收益）

- **上下游依赖影响量化**（结合定性 + 定量评估）：
  - **上游依赖风险**：需新增/升级的 `@deepseek-ai/*` 包数量、dsh 版本跨度、上游依赖维护活跃度与破坏性变更预告（rc.x → rc.1）
  - **下游扩散范围**：直接修改的模块数量、被该模块间接引用的插件/客户端模块总数（如 SessionEventMap 声明合并、投影类型表、events.ts / rules.ts 公共模块）
  - **连锁反应预判**：修改是否触及 `@deepseek-ai/dsh-session/types` 类型合并、投影 schema、公共类型定义等易产生广泛影响的文件
  - **兼容性扩散**：是否因升级 dsh / `@deepseek-ai/*` 依赖，导致宿主与客户端两侧需同步调整代码

- **若收益确实无法量化**（如"提升代码可读性"），须定性说明**预期可观测的改善迹象**（如"模块圈复杂度从 12 降至 6"或"新成员上手时间预期缩短 40%"），并给出验证方法（如 Code Review 评分、单元测试覆盖率）。


### 第九章 执行过程规范

1. 严格按确认后的方案执行，不擅自增删功能或调整范围（如不额外引入未提及的第三方库）。
2. **OpenSpec 工作流衔接**：
   - 探索过程遵循 `openspec/config.yaml`：不确定点（需求、UI 交互、功能点细节、上下文依赖、技术栈选择、公共组件/库）必须列出待确认清单，禁止假设；探索结束后必须先退出探索模式创建提案，禁止直接执行。
   - 执行前准备：运行 `openspec status --change <name> --json` 与 `openspec instructions apply --change <name> --json`，按其 contextFiles 读取 proposal / design / specs / tasks 等上下文文件后再动手。
   - 属文件变更的任务必须写明**变更文件路径**与**完整变更内容**（以 diff 新增/删除/修改行形式呈现），禁止只写文件路径而无 diff 片段。
3. 复杂方案须**分步执行**，每完成一个关键里程碑（如"通过 typecheck""通过单元测试""通过 Sub-agent 任务审计"）向用户汇报进度。
4. **逐个完成**：按 tasks.md 顺序逐个完成任务，每完成一个任务立即将 `- [ ]` 置为 `- [x]`，禁止跳步或批量勾选。
5. **变更聚焦**：每个任务只做该任务要求的最小、聚焦改动，避免无关重构与过度设计。
6. 若执行细节与方案存在轻微出入（且未达到 L2/L3 变更标准），在当次进度汇报中**主动说明偏差及原因**。
7. **审计闭环**：每个 spec 执行完成后，立即执行 Sub-agent 任务审计（对照 capability spec 与 design 契约）；审计发现问题必须修复并重新审计直至通过。
8. 遇阻断性问题（如目标 dsh 版本无该 API、依赖版本冲突、契约与文档不符），立即停止并汇报，不自作主张改道。
9. **自主解决**：遇到阻塞问题优先尝试自主解决，仅在无法解决时才向用户提问；执行已确认任务时禁止不必要的提问，须完整执行所有任务（含单元测试、验证、审计等收尾任务）。
10. 完成后汇报：执行完成后一次性汇报全部任务完成情况，不中途汇报进度；保持最小消耗（最少调用、最低消耗）。

#### 附录 D：项目代码风格与安全合规速查（源自 AGENT.md）

| 类别 | 要求 |
|------|------|
| 组件开发 | 优先函数式组件 + React Hooks，禁止类组件 |
